readme / apiproof

Trace Stripe API changes to the code that depends on them.

ApiProof compares two OpenAPI documents you supply, looks for TypeScript and JavaScript call sites that may depend on what changed, and writes evidence for a human to review. It reads local files. It does not call Stripe.

What it is

A small command-line tool and GitHub Action for an early, specific problem: a Stripe API contract changes, and you need to know which parts of your repository might be affected before you review or ship. It is local-first and produces files you can read, diff, and keep.

It is not a hosted service, a Stripe dashboard, or a verification engine. The current verification runner is deliberately not configured; that fact is part of the output, not hidden behind a green check.

What it does

Compares supplied contracts. It detects supported structural changes in old and new OpenAPI JSON: removals, type changes, requiredness increases, and removed enum values. Local component-schema references are supported.

Finds likely call sites. It inspects TypeScript and JavaScript with ts-morph and reports statically identified Stripe client usage that references changed fields. Each finding carries evidence and confidence.

Writes review artifacts. It produces machine-readable impact JSON and a Markdown evidence report. Findings are leads to investigate, not proof of a runtime failure.

What it cannot do yet

  • Fetch Stripe specifications or call the Stripe API.
  • Run old and new application scenarios. verify returns could_not_run because the isolated runner is a stub.
  • Prove runtime behavior or complete call-site coverage.
  • Invent a replacement field or semantic mapping. Unsupported changes return needs_human.
  • Apply patches to your files. There is no CLI fix command today.
  • Handle external or nested JSON Pointer references, dynamic client construction, REST calls, generated or vendor code.

Setup

Node.js 20 or newer and npm are the only requirements.

git clone https://github.com/D1bakar/Dokimana.git
cd Dokimana
npm ci
npm run build
npm start -- doctor

doctor checks the key environment for unsafe values. A missing key is reported as not configured and is not an error.

How to use it

Run a scan against the checked-in synthetic fixture pair to see the shape of the output. These files are not a real Stripe release baseline.

npm run dev -- scan \
  --repo . \
  --old fixtures/stripe-old.json \
  --new fixtures/stripe-new.json \
  --old-version fixture-old \
  --new-version fixture-new \
  --json apiproof-impact.json \
  --markdown apiproof-evidence.md

Add --fail-on-changes true to exit with status 1 when structural changes are found. Reports are written before that gate is applied.

Build a Markdown report from an existing impact file:

npm run dev -- report \
  --repo . \
  --impact apiproof-impact.json \
  --provider-version fixture-new \
  --output apiproof-evidence.md

Check key safety and verification status. A valid scenario still returns could_not_run and exits unsuccessfully until a real isolated runner exists.

npm run dev -- doctor
npm run dev -- verify --repo . --scenario ./scenario.json --json verification.json

In CI, the GitHub Action scans workspace-relative OpenAPI files and writes the same two reports. It does not download inputs or call Stripe. Pin and review those inputs in your own workflow.

How it is different

No superiority claim is being made here. These are concrete boundaries you can check in the source:

  • Your OpenAPI inputs and repository stay local; no provider is fetched.
  • A scan needs no Stripe key, and live keys are refused where keys are checked.
  • Findings carry evidence and confidence instead of a bare pass or fail.
  • Unsupported changes stay needs_human rather than becoming guesses.
  • Missing verification is reported as could_not_run, never as a pass.
  • Nothing is written to your source files automatically.
